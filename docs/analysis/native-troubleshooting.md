# REA / Ghidra Windows 原生研究工具诊断

日期：2026-10-10。本报告描述研究工具的通路与限制，不公开商业样本身份。目标路径、文件名和摘要仅保留在本地私有证据中。

## 已验证结果

官方Ghidra 12.1.4与JDK21在本机对一个小型x86 DLL完成静态分析，约40秒退出0；这只证明引擎对该目标可用，未证明REA桥接、主程序函数分析或整个应用重建成功。

REA 6.3.0的Windows Ghidra P0拒绝DLL目标。主程序和模拟器的原生索引分别在300秒与120秒超时，失败回执保留；未为了得到成功反复无界重跑。

## 两次直接诊断

| 匿名记录 | 操作 | 结果 |
|---|---|---|
| A-NATIVE-01 | 原安装目录目标，关闭自动分析 | 退出255，路径/引号处理失败 |
| A-NATIVE-02 | 独占目录同摘要副本，开启有界分析 | 退出0，导入和分析成功；有类型/依赖恢复局限 |

两个测试既有路径差异也有分析模式差异，因此不能把它们当作单变量实验，或声称已找出REA超时根因。没有执行目标DLL、修改原安装或产出完整主程序伪代码。

## 源码观察与下一步

REA桥接以postScript在自动分析之后运行；timeout错误转换没有保留全部详细诊断。当前失败不足以区分导入、自动分析、桥编译、端点和握手阶段。

后续先保存provider日志和分阶段耗时，再选当前provider接受的小型PE application验证。不要把DLL改名绕过角色检查，也不要只增大超时重复分析大程序。请求超时、文件分析超时、CPU/堆限制须分别设置并验证实际命令。

直接Ghidra结果与REA Evidence分别记录；没有返回的函数、xref与伪代码继续标未知。详见[研究总览](overview.md)和[路线图](../../ROADMAP.md)。
