# 项目命名、开源与商业模式建议

日期：2026-10-10，Asia/Shanghai。本文保留早期研究与报价假设。后续用户已选择中文名“可编程人机界面平台”、英文名 **HmiCraft**，授权在 IoTSharp 组织创建同名私有仓库并推送；当前决定以 [知识库](../knowledge/README.md) 为准。许可和售价仍待定稿，没有添加 LICENSE、注册域名或开展销售。

用户最终明确同时面向 **设备厂商/OEM** 和 **开发者与小团队**，并且 **自己销售设备、支持第三方 OEM、提供定制服务**。因此推荐“开源平台 + 自有品牌 HMI 设备/开发套件 + Pro 效率工具 + OEM/定制交付”。本文建议同时支持采购本方硬件贴牌、第三方自研兼容硬件两条合作路径，具体合同条件仍待决定。开发者渠道与 OEM 产品化相互衔接；既有工业 HMI 需求和 IoTEmbedded/LVGL/BASIC 技术路线保持独立，学习套件不能冒充工业成品。

## 建议结论

- 名称已由用户最终选为 **HmiCraft · 可编程人机界面平台**。品牌和产品族按此统一，技术标识另做兼容迁移。
- 社区版必须能够完成实际设备项目，支持商业使用、离线编辑、生成、模拟和基本部署；开源运行时不按每块 MCU 收取运行授权费。
- 主要产品收入建议来自自有品牌 HMI 整机/模组和开发套件。先用一个经过验证的套件完成闭环，再小批量交付标准工业机；Pro 与 OEM 适配/长期支持是增值收入，不把卖编辑器作为唯一盈利支点。
- Pro 按开发者席位收费，建议买断当前主版本、包含 12 个月更新；不续升级时继续使用已授权版本，已交付设备继续独立运行。
- 开源许可建议：新设备运行时/SDK/模板和示例代码采用 MIT；设计器与生成器的社区部分采用 MPL-2.0；独立编写的 Pro 扩展可采用商业许可。先完成文件归属和第三方清单，再正式选择并发布。

## 已确认的品牌与产品族

采用 HmiCraft；近似名称、商标、域名和包名仍需发行前核查。产品族建议统一为：

1. **HmiCraft Studio**：设计器，分 Community 与 Pro 版本。
2. **HmiCraft Runtime**：设备执行层；技术说明注明基于 IoTEmbedded 与 LVGL。
3. **HmiCraft Kit**：预置可恢复固件、教程与示例的开发套件。
4. **HmiCraft Panel**：自有工业 HMI 整机/模组；具体型号在屏幕和硬件冻结后确定，品牌方案不先承诺某个型号已上市。

中文名称为“可编程人机界面平台”，品牌不加 IoTSharp 前缀。不承诺 VB6 语法、COM 或二进制兼容。

## 市场定位与需要验证的优势

已有多类公开资料对照：开源方案已覆盖低代码、LVGL编辑与支持服务；商业工具已有设计、预览、订阅与运行时资源更新；设备配套工具采用降低工具门槛、硬件形成收入的路径。来源用市场样本B/C/D匿名登记，真实链接只留私有研究记录。这些是资料研究，不能当作统一任务集的实测。

因此，“无需重新编译固件”本身不能宣称为独有创新。我们需要在完整工作流、硬件验证和恢复可靠性上证明价值。

据此，我建议本项目集中验证这套组合价值：VB6 式对象/属性/事件体验，BASIC 业务逻辑，GPIO/传感器/Modbus 绑定，同一资源包的主机与设备运行，以及可靠的独立更新。市场表达可以是“拖出界面，写好事件，让设备运行”。这些是待实现和待客户验证的价值，不是已经具备的功能。

用户已明确要求整合 `IoTSharp/lvgl-editor` 并评估在线优先；已作为固定子模块接入，两个 PR 按差异选择性采纳。真实源码研究和新增 LVE 路线见 [在线整合分析](../analysis/lvgl-editor-integration.md)，不再仅依据其 README 判断成熟度。

## 为什么建议开源

以下是针对开发者客户的经营判断：开放运行时、格式和基础工具，有助于用户评估停服风险、调试板卡问题、复用模块并向同事推荐。与之对应的成本是维护社区、回答问题、接受合法 fork，以及竞争者可能复用代码。开源不会自动带来贡献、用户或收入。

| 方案 | 对当前首批客户的判断 | 收费逻辑 |
|---|---|---|
| 全闭源设计器与运行时 | 新用户需先相信小团队会长期维护；采用门槛较高 | 必须尽早证明明显优势，适合已有客户渠道时考虑 |
| 所有组件 MIT，收入只靠支持 | 接入简单，但难形成独立 Pro 产品边界 | 依赖硬件销量、适配和支持；可行但需要足够服务能力 |
| 开源社区核心 + 自有设备/套件 + 独立 Pro 工具 | 推荐，既让免费用户完成项目，也提供经过验证的硬件交付 | 整机/模组/套件为主，工具席位、OEM 适配和维护为辅 |

真正的开源应允许商业使用和分发；不能在标准开源许可上追加“禁止商用”或“禁止竞争产品”后继续按 OSI 定义宣称开源（S6）。源码可见与开源不是同一承诺。我的建议是接受合法竞争，用易用性、稳定性、教程、测试过的板卡和持续迭代建立优势。

## 许可与产品边界建议

针对“具体开源什么、不开源什么”，推荐以下清单。它是待批准政策，不代表相应功能已经实现，也不为尚未审查的第三方代码重新授权。

| 范围 | 建议公开程度 | 具体边界 |
|---|---|---|
| 工程/包格式、BASIC HMI API、board profile、部署与扩展接口 | 开放规范和自测语料 | 第三方无需私有工具或官方激活服务器也能接入兼容设备 |
| HMI runtime、LVGL 封装、BASIC 绑定、事件/变量/资源与加载恢复 | 开源 | 可自行构建、修改、商用；基础执行预算、错误诊断和恢复不成为付费门槛 |
| 社区设计器、工程模型、生成器、基础模拟/部署 | 开源 | 免费用户可完成真实项目，不能只有画布而无法生成或下装 |
| 通用 BSP、GPIO/ADC/PWM/输入/存储和自有协议实现 | 按所属项目开源 | 通用内容归 IoTEmbedded，HMI 适配归本仓；保留准确第三方许可；不复制永久私有通用驱动分支 |
| 官方入门示例、生成模板、基本控件/公共扩展 SDK | 开源 | 用自有或获授权的资源，模板许可明确，便于客户商用工程 |
| Pro 高级调试 UI、资源分析、工程合并和批量交付效率工具 | 独立商业模块 | 运行时基础诊断接口保持开放；社区仍可做基本调试/日志查看；不能把 MPL 覆盖代码的改动直接藏入商业文件 |
| 企业设备管理、协作审批、批量生产工作流及托管服务 | 可闭源或收费服务 | 不成为离线设计、基础设备运行和普通更新的强制依赖；嵌入式基础安全/恢复留公共核心 |
| 量产 PCB/Gerber、生产工装细节、BOM 采购价和供应链资料 | 首期不公开 | 公布客户接入需要的电气/机械/通信规格；硬件设计授权另约，不把保密资料夹进公共仓库 |
| 客户专属业务脚本、配方、界面、算法、行业工艺和私有集成 | 默认保密，权属按合同 | 不自动进入平台公共仓库；公开案例和通用化复用需具备相应权利 |
| 设备私钥、签名材料、客户凭据与现场数据 | 不公开 | 与商业代码是否开源无关，不能进入公开源码或示例 |

判断免费社区版是否完整：用户能在支持的设备上独立完成“编辑→生成包→运行→基础外设/协议→更新与恢复”。判断 Pro 是否合理：它让批量和复杂工程更高效，而不是把这条基本链路截断。

### 定制服务的成果划分

1. **通用适配与平台修复**：如新 BSP、显示驱动、公共控件修复，默认作为框架改进维护。客户购买开发、联调、验证和交付服务，不默认购买独占权；公开/提交范围在合同中明确，不能未经授权公开客户现场资料。
2. **专属业务实现**：客户工艺、配方、页面、私有协议映射和业务算法独立存放，默认按合同保密和交付，不回流公共示例。
3. **排他/买断要求**：开工前单独明确可授予的权利、第三方依赖和报价；已开放的公共代码不能承诺被客户独占，也不能承诺排除仍然有效的开源义务。
4. **后续维护**：源码修复、稳定分支维护、验证组合和响应服务分别描述。建议公共核心修复仍可获得，收费的是约定维护周期、回归验证和服务响应；不将基础安全修复完全变成付费特权。

定制合同至少区分平台既有代码、本次通用改进、客户专属成果和第三方组件，并约定各自权利、公开范围、验收与维护边界。发布代码与对外提交仍需按项目授权执行，本轮没有做此类操作。

| 部分 | 建议 | 原因与条件 |
|---|---|---|
| IoTEmbedded 子模块 | 保留固定提交的 MIT 及第三方声明 | 已核对本地和固定 SHA 的根 LICENSE；其内置 MY-BASIC 文件也带 MIT 文本；不将根许可泛化为所有第三方组件许可（S7/S8） |
| 新设备 runtime、HMI API/SDK、生成代码模板、示例代码 | MIT | 便于用户把设备应用用于自有产品；保留所需版权和许可信息，模板与生成器代码分开授权 |
| 社区设计器与生成器 | MPL-2.0 | 希望已覆盖文件的分发修改保持可获得，同时允许独立扩展；不期待它阻止竞争者商用（S9） |
| 独立 Pro 工具模块 | 商业许可 | 付费功能必须有清楚代码边界；若修改/包含 MPL 覆盖代码，仍履行该部分义务，不能把整个 Pro 程序一概称为闭源（S9） |
| 用户工程、脚本、资源 | 明确用户自有内容的权利；第三方内容依其原许可 | 不因使用设计器就主张用户业务逻辑所有权；生成模板和运行库的 notices 另列 |
| 图标、字体、图片、硬件文件、品牌 | 单独列明来源和许可/使用政策 | 不由代码许可证自动推导其使用权 |

软件开源不意味着必须同时开放量产硬件的所有生产资料。建议公开电气接口、接线、协议、扩展接口和必要参考设计，量产 PCB/Gerber、制造测试工艺及供应链信息先独立管理；是否开放硬件作为后续商业决定。官方品牌、已测试固件组合、生产测试、供货和质保是设备价值的一部分。避免将软件开放宣传为整机硬件也已开放。

MPL 的主要边界是文件级：对外分发涉及修改的覆盖代码时需履行相应源码提供义务；企业内部私有修改不等于必须公开上传。独立、不含 MPL 代码的新文件可以采用其他许可（S9）。正式发布前应由熟悉软件许可的专业人士复核分发组合和商业条款。

本次核对的 IoTEmbedded、MY-BASIC、LVGL 核心与 Avalonia 12.1.4 均有 MIT 许可依据（S7/S8/S10/S11），但这不是完整固件或安装包的许可审计。LVGL 核心许可与外部商业工具许可分别处理；将来选用字体、图片解码库、TLS、板卡 SDK 和网关时再核对准确版本。

先明确贡献政策及各文件权利人。若日后考虑双重授权，需另外核对所有相关贡献的授权链，不能默认收到 PR 就获得任意改许可证的权利。当前不以未来必能改成闭源作为商业前提。

## 免费与付费应如何划分

社区版建议提供完整基础链路：多页面设计、基础控件、用户 BASIC、生成/模拟、普通下载、GPIO/温度/Modbus 基础绑定、日志与错误定位、运行预算及恢复机制。可商业使用，可在支持的自有板卡运行；不靠强制联网、付费保存/导出或人为极低页面限制推动升级。设备的真实内存/性能限制仍必须执行。

Pro 建议出售节省时间的工具，先选需求最强的两项实现，再扩展：

- 可视化脚本调试：断点、调用栈、变量观察及事件轨迹。
- 资源与性能分析：字体/图片占用、脚本耗时、堆栈与页面成本定位。
- 工程差异/合并辅助、可复用组件维护、批量部署和测试报告。
- 后续团队私有组件库与协作；如需托管服务，单独订阅，不成为离线编辑的前提。

基础诊断、故障恢复和脚本预算留在社区核心；高级分析 UI 和自动化工作流可作为 Pro。只把官方验证过的板卡列入套件支持范围，社区适配板标明其验证状态；开放驱动 API 不代表承诺为每种 DIY 板卡提供免费适配。

## 商业模式和定价试验

收入优先级建议为 **自有设备/开发套件 → OEM 适配与维护 → Pro 席位**；三项按交付成熟度逐步开展，模板商城和云平台后置。开发者套件降低入门门槛，OEM 客户通过标准模组/整机及批量价格把项目转为产品。两类客户共用核心软件，但交付物、支持范围和价格分别定义。

套件应出售“可以复现成功的完整体验”，包括固定板卡/屏幕、预置与恢复固件、线材、教程和可运行示例。自有设备可采用成熟模组和外包制造，团队掌握产品规格、固件、BOM 版本、测试工装与售后，不需要一开始自建工厂。先小批量验证，不以计划销量大量备货。

标准工业机应包含满足其规格的 24V 输入、屏/触控、RS485/网络、结构和出厂测试；基础设计工具、基础运行固件、必要修复与恢复说明随产品可用。扩展采集模块可以单列，不能用低价裸屏价格宣传为完整工业配置。OEM 报价按“适配开发费 + 阶梯硬件单价 + 可选年度维护”展开，另列开模、起订量、变更、供货周期和停产替代要求。

下列是建议拿去访谈和试销验证的人民币定价假设，不是市场调查均价、已承诺售价或营收预测：

| 产品 | 价格试验 | 权益边界 |
|---|---|---|
| Community | 免费 | 可完成基础设备项目，可商用 |
| Studio Pro 单席位 | 499～999 元；可先测试 699 元 | 买断当前主版本，含 12 个月更新；后续升级可选；不收已交付设备运行费 |
| 小团队 3 席位包 | 1,799～2,499 元；可先测试 1,999 元 | 同一工具权益、许可管理与限定范围支持；不承诺无限技术服务 |
| 官方开发套件 | 根据准确 SKU 和单位成本定价 | 可附 Pro 限时体验或升级折扣；含必要入门支持，定制适配另计 |
| 标准工业 HMI 整机/模组 | 按完整配置、测试/质保成本及渠道分别定价 | 基础编辑和运行不再额外收设备激活费；客户买到可独立运行的设备 |
| OEM 批量产品 | 一次性适配费 + 数量阶梯单价 + 可选维护 | 标准产品优先，定制范围、交期与验收分别约定 |
| 板卡适配/专项支持 | 按明确范围单独报价 | 在产品方向吻合时接单，不能让无边界项目消耗基础产品开发能力 |

价格档位需配套测试：例如 699 元单席位与 1,999 元三席位是同一组；不能拿最低单席位价格配最高团队价格。教育/开源项目折扣待实际支持成本明确后制定。

套件建议使用贡献毛利测算：

`目标售价 = 单套可变成本 / (1 - 目标贡献毛利率)`

单套可变成本应含板屏、配件、装配测试、包装、支付/平台费用、运费承担、预计售后备件与入门支持；税费口径一致。可以先用 30%～40% 的目标贡献毛利做方案筛选，这只是管理目标。贡献毛利仍需覆盖研发、固定费用和市场支出，不能当净利润。既有硬件草案的 700～1,200 元是工程样机预算，不可直接作为套件销售成本或售价。

如果为了降低开发者入门价格推出简化套件，应建立单独 board profile 和能力表；没有 24V/隔离 IO 的学习套件不得宣传为工业成品，也不改变已经确认的工业 HMI 目标。

运行时若按 MIT 开放，应允许用户自行构建和商用。日后 OEM 收费对象可以是适配、官方固件维护、批量测试、品牌服务或独立商业模块，而非把开源运行时的正常使用重新包装为必付授权费。

## 第三方 OEM 合作边界

用户确认支持别人 OEM；建议在产品和合同上区分以下路径，避免将软件许可、硬件供货和品牌许可混在一起：

| 合作方式 | 合作方获得什么 | 我方收入 | 保留的边界 |
|---|---|---|---|
| 采购本方模组/整机再贴牌 | 可交付硬件、明确版本的固件、品牌配置与文档 | 硬件价差、包装/固件定制费、可选维护 | 规格、起订量、质保、停产替代与客户支持责任明确 |
| 第三方自研/生产兼容设备 | 开放运行时、接口/包规范、板卡适配入口 | 可选 BSP 适配、验证、工具席位、LTS 与支持 | 不强制采购本方硬件；按所选开源许可保留必要声明，官方认证/品牌另行处理 |
| 获得本方量产硬件设计资料并制造 | 合同约定范围的原理图/PCB/生产资料和协助 | 一次性工程/设计授权费，是否按量收费另约 | 仅限我方有权提供的设计资料；不扩大为对开放运行时或第三方独立设计收取必付费用 |

官方认证应代表实际的兼容性验证、版本组合和问题响应，不是买一个徽章。可以提供公开自测套件；“官方认证”标识需实际通过对应测试并按品牌政策使用，不认证的兼容设备仍可依据开源许可运行。软件开放不自动授权使用 IoTSharp 的商标、宣传为官方产品或承诺我方质保。

为减少与伙伴竞争的摩擦，建议直营聚焦标准开发套件与标准 HMI，伙伴覆盖行业渠道和定制设备；分别定义零售、模组/OEM 与服务报价。对伙伴提供其交付所需的版本、资料和稳定接口，而不是突然把已开放功能收回收费。开源分发要求的版权/许可信息和产品外观品牌分别处理。

这会给工程增加明确要求：第三方 board profile、公开包/API 合同、可配置品牌信息、独立 BSP 接口、固定版本兼容矩阵和可重复测试。签名/安全启动的设备信任根由设备制造方按产品管理，不将本公司授权服务器变成所有兼容设备运行的强制前提。IoTEmbedded 仍负责通用能力，本仓负责 HMI 语义与兼容测试。

## 获客和推进顺序

1. **完成一个可信演示**：一块板、一种屏，触摸与实体按键、温度或模拟传感器、GPIO/Modbus，再只更新 BASIC/资源并展示基础固件未变；保留恢复流程。
2. **找 10～20 名目标开发者试用**：建议访谈样本，不是已有客户。观察从开箱到首次运行耗时、卡住的步骤、第二个工程是否继续使用；分别询问工具和套件付费意愿。
3. **围绕三份完整教程发布社区版**：温度监测屏、Modbus 状态面板、按钮/PWM 小实验。源码、工程、接线、固件版本一致；中文文档先行，英文快速开始同步。
4. **小批量销售经过验证的套件**：明确交付和支持范围，记录实际单位成本、退换原因和支持时间，再决定库存规模。此处是计划，本轮不采购或预售。
5. **用真实重复痛点决定 Pro 第一项功能**：先验证调试器或资源分析器是否足以让人付费，不先做大量许可、商城和云端系统。
6. **同步接触 2～3 家 OEM 试点**：作为建议目标，不是已有订单。优先使用同一标准板/整机，形成小批量付费验收，再提供长期维护、专用 BSP、白标发行和批量集成；保持开源权利与付费服务分开。

产品节奏建议是“开发套件验证 → 标准工业 HMI 小批量 → 基于标准产品的 OEM”。避免首期同时定制多种主控/屏幕/外壳，把资源集中在一个可持续生产和支持的基线。

建议按上述事实做继续/调整决策，而非以 GitHub stars 代替需求：首次成功率、四周内再次使用、套件贡献毛利、每单支持工时、Pro 实际付费转化、退款率。试用样本过小时只作探索，不据此承诺市场规模。

## 与当前路线的衔接

本建议不改动现有 E0/IEB/HMI/INT 任务的完成状态。商业公开发布前增加独立检查：品牌及域名确认、相关 IoTSharp 项目定位、许可与第三方清单、社区/Pro 功能边界、一个可复现真机闭环、套件成本和支持政策、第三方 OEM 路径与认证/品牌边界。外部样本 原二进制、提取文档与原资源继续留在分析区，不作为新产品分发材料。

当名称和许可获正式决定后，再统一改品牌、仓库标识、命名空间及兼容迁移说明。当前 `.hmistudio.json` 是已存在的工程格式；名称变化不应导致用户文件突然打不开。
